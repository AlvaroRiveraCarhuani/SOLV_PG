# ADR-046: Constructor de Entornos Componibles por Catálogo de Tecnologías y Construcción Local Determinista de Imágenes (`solv-local/stack:<sha256>`)

- **Estado:** Aprobado
- **Fecha:** 2026-10-19
- **Contexto:** Core / Gestión de Entornos y Gobernanza Docker

## Contexto y Problema

El flujo original de registro de plantillas se basaba en un modal multipaso de 6 pestañas que presentaba tres limitaciones estructurales:
1. Duplicación de la selección de modelos preconfigurados entre el paso de identidad y el paso de imagen.
2. Imposibilidad de combinar tecnologías de distintos ecosistemas (por ejemplo, un lenguaje backend como Python con una plataforma frontend como Angular y un motor de base de datos acoplado) sin escribir manualmente comandos de aprovisionamiento o construir imágenes externas.
3. Exposición directa de vocabulario de infraestructura (`tags OCI`, `cgroups v2`, `memory.high`, `smoke test`) en la interfaz principal para administradores académicos y docentes.

Si las dependencias adicionales se instalan únicamente en el script de inicio (`setup_script`) cuando el estudiante abre su contenedor, un curso de 30 alumnos entrando simultáneamente multiplica el tráfico de red y el tiempo de arranque. Por otro lado, depender exclusivamente de imágenes pre-armadas en registros externos impide combinar tecnologías a medida o incorporar herramientas nuevas.

## Decisión

1. **Catálogo Extensible de Componentes Tecnológicos (`template_components`), Motores de Base de Datos Gobernados por el Nodo (ADR-045) y Activos Vectoriales Oficiales (`public/tech-icons/`):**
   - Se modela un catálogo persistente en PostgreSQL clasificado en tres capas componibles: `runtime` (lenguaje principal e interfaz web opcional), `addon` (complementos, librerías, drivers y ORMs con matriz de compatibilidad `compatible_runtimes`) y `database` (servicios acoplados).
   - La Columna 3 (`Base de Datos`) es una capa de catálogo gobernada, no cerrada: el administrador registra y activa motores con `layer: "database"` y `service_engine` dentro del dominio soportado (`none`, `sqlite`, `postgres`, `mysql`, `mariadb`, `mongodb`, `redis`), con inferencia automática desde `slug`/`name`/`icon_key`/`base_image` y valores por defecto deterministas para `sub_category` (`relational`/`nosql`), `base_image` con tag fijo y `ram_delta_mb`. Un motor se aprovisiona como servicio y nunca se instala dentro de la imagen del laboratorio (`install_mode: none`). Los clientes de base de datos u ORMs (`Prisma`, `SQLAlchemy`, `TypeORM`) se registran en el catálogo abierto como `addon`.
   - Las capacidades del nodo (`GetRuntimeCapabilities`, ADR-045) exponen los seis motores soportados con `is_available: true` y su `provisioning_mode`: `embedded` para SQLite3 nativo (`+0 MB RAM`), `shared_host` para el PostgreSQL de aula (`~50 MB RAM`, con versión mayor detectada en vivo vía `SHOW server_version;` en `PostgresVersionProbe`) y `managed_container` para MySQL, MariaDB, MongoDB y Redis, que se levantan bajo demanda y se apagan solos. El modo de aprovisionamiento reemplaza al bloqueo por variables de host manuales (`MYSQL_SATELLITE_HOST`, `MONGODB_SATELLITE_HOST`, `REDIS_SATELLITE_HOST`), que quedan solo como override de destino para un motor externo ya provisionado.
   - Se incorpora un modo de alta guiada por **Tarjetas de Catálogo Contextual en 1 clic** para Lenguajes Principales (`OFFICIAL_ECOSYSTEM_PROFILES`: `c-gcc13`, `cpp-gcc13`, `python-312`, `java-21`, `node-20`, `go-122`, `rust-stable`, `php-83`, `dotnet-8`), Plataformas Web (`OFFICIAL_WEB_PROFILES`: `angular-web`, `react-vite`, `vue-vite`, `vite-web`) y Kits de Complementos filtrados por ecosistema (`OFFICIAL_ADDON_PRESETS`) en `ComponentFormModalComponent`, junto con el motor de inferencia en backend (`NormalizeCreateComponentDTO`).
   - **Parametrización Abierta de Versiones (`imageTemplate` + `suggestedVersions` + entrada libre):** Cada perfil expone la versión recomendada LTS/estable preseleccionada por defecto (para usuarios que no requieren especificar versión) junto con chips de versiones anteriores/recientes y un campo abierto de versión para que docentes o administradores puedan indicar cualquier versión específica o futura (ej. `3.10`, `3.14`, `17`, `22`, `14.2`), resolviendo dinámicamente el tag oficial sin exigir conocimientos de Docker Hub.
   - **Detección en Vivo de Piezas Instaladas (`En catálogo`) y Prevención de Conflictos `409`:** El modal cruza cada preset contra el catálogo activo, priorizando primero las tecnologías aún no instaladas, marcando con el indicador semántico `En catálogo` las ya existentes, y convirtiendo automáticamente el guardado en una actualización idempotente (`PUT`) si el administrador selecciona una pieza ya registrada, además de ofrecer la tarjeta `+ Personalizado` para limpiar el estado cuando desea registrar una tecnología manual desde cero.
   - **Gestores de Paquetes de Primera Clase en Servidor (`SynthesizeAssistedBuildLayer`) y Filtrado por Ecosistema:** Se amplía el dominio en Go (`InstallMode`) y la restricción `CHECK` en PostgreSQL para sintetizar y validar en servidor (con `ValidatePackageNames` contra inyección de shell) todos los gestores modernos: `pip`, `uv` (Python), `npm`, `pnpm`, `yarn`, `bun` (Node.js / Web con `corepack`), `apt` (C/C++/Java/Sistema), `cargo` (Rust), `go` (Go), `composer` (PHP) y `dotnet` (.NET tools), bloqueando en la interfaz gestores incompatibles con el lenguaje padre seleccionado y resolviendo dinámicamente la imagen base web desde el runtime Node activo del catálogo.
   - Los parámetros de bajo nivel de contenedor (imagen base manual, comando de evaluador personalizado, binarios de verificación y perfil manual de memoria) quedan encapsulados bajo el panel colapsado **Modo experto (contenedor)**, manteniendo la vista principal libre de configuración de infraestructura. En la verificación del entorno (`RunSmokeTest`), los paquetes instalados por sistema se validan tanto por binario en `PATH` (`command -v`) como por registro de paquetes (`dpkg -s` y `apk info -e`).
   - Se reemplaza el bloque condicional inline (`@switch`) de iconos en `TechLogoComponent` por un paquete de activos estáticos vectoriales oficiales (`frontend/public/tech-icons/<slug>.svg`) incluyendo iconos diferenciados para `c.svg` y `cpp.svg`.
   - `TechLogoComponent` y `ComponentFormModalComponent` aceptan además rutas locales (`/tech-icons/...`), URLs externas (`https://...`) o URI de datos (`data:image/svg+xml,...`) en `icon_key`, con degradación automática a monograma determinista de 2 letras ante claves personalizadas o errores de carga (`error` en `<img>`), siendo 100% compatible con despliegues On-Premise sin conexión a internet y futuros entornos híbridos o en nube.

2. **Construcción Local Determinista de Imágenes direccionada por Contenido (`solv-local/stack:<sha256>`), Bootstrap Multi-Distro y Compatibilidad de Imágenes Base:**
   - Cuando una plantilla utiliza únicamente un lenguaje base sin capas adicionales de construcción, resuelve directamente a su imagen oficial fijada.
   - Cuando combina múltiples capas (ej. `Python 3.12 + Angular + FastAPI`), `TemplateComposerService` calcula un hash SHA-256 determinista de 12 caracteres sobre la imagen base y las capas ordenadas, generando el tag inmutable `solv-local/stack:<sha256>`.
   - Al combinar una Plataforma Web (`Angular`, `React`, `Vue`) con un lenguaje base que no sea Node.js (ej. Python, Java, Go, Rust), el generador inyecta un bootstrap multi-distro tolerante a distribuciones Alpine y Debian/Ubuntu:
     `RUN (command -v apk >/dev/null 2>&1 && apk add --no-cache nodejs npm) || (apt-get update && apt-get install -y --no-install-recommends nodejs npm && rm -rf /var/lib/apt/lists/*)`
   - La imagen semilla para `java-21` se actualiza de `eclipse-temurin:21-jdk-alpine` a `eclipse-temurin:21-jdk-jammy` (vía migración `00023_update_java21_base_image.sql`) para garantizar compatibilidad con `glibc` y la extensión de OpenVSCode Server en el nodo.
   - Durante la verificación del entorno (`EnvTestService` + `ImageBuilderPort`), si el tag ya existe en el daemon Docker local del nodo, se reutiliza de inmediato (< 0.2 s); si no existe, se construye una única vez en el servidor aprovechando la caché de capas `overlay2`.
   - Se ejecuta recolección de basura automática (`PruneOrphanStackImages`) para eliminar imágenes `solv-local/stack:*` no referenciadas por plantillas activas o pendientes.

3. **Modelo de Memoria por Perfiles Académicos, Barra Segmentada de 3 Tramos Reales (`memory-bar`), Estimación Unificada de Capacidad y Candados de Seguridad:**
   - Tanto `TemplateComposerService` en Go como `TemplateStudioComponent` en Angular calculan la memoria recomendada (`recommendedRamMB`) y el mínimo requerido (`minimumFloorMB`) a partir de la huella de los procesos en ejecución (`editorBaseMB = 210 MB` en `IDE_PERSISTENTE` o `32 MB` en `JUEZ_EFIMERO`, más `satelliteBaseMB` del servicio acoplado como `50 MB` en PostgreSQL Aula o `0 MB` en SQLite, más la huella del proceso activo), sin sumar linealmente las librerías instaladas en disco (`pip`/`npm`/`apt` con perfil `library`), evitando inflar cuotas por paquetes pasivos.
   - En lugar de botones estáticos con nombres fijos de tecnologías, la Sección 3 de `TemplateStudioComponent` sintetiza dinámicamente dos perfiles académicos claros orientados a la planificación docente:
     - **Perfil Estándar (Recomendado):** asigna la cuota óptima recomendada (`recommendedRamMB`) para clases semanales, algoritmos y prácticas guiadas con la mayor cantidad de alumnos simultáneos.
     - **Perfil Intensivo (Holgura para proyectos):** habilita el siguiente escalón de memoria (`intensiveRamMB`) para compilaciones pesadas, ejecución de múltiples pruebas o manejo de datos extensos (omitiéndose si la selección base ya alcanza el tope máximo del servidor para evitar claves duplicadas).
   - Se unifica la métrica de capacidad del aula eliminando duplicaciones: la capacidad nominal (`nominalConcurrentStudents`) se calcula dividiendo la memoria permitida del servidor entre la cuota por alumno (`maxAllowedRamMB / baseRamMB`), sin volver a sumar la base de datos al divisor puesto que ya se encuentra contemplada en la cuota base.
   - La barra gráfica segmentada `.memory-bar` divide la cuota en 3 tramos reales cuya suma cierra con precisión al 100% de la memoria asignada:
     1. `Motor de evaluación` / `Editor de código` (`editorBaseMB`: 32 MB o 210 MB).
     2. `Tecnologías elegidas` (`stackBaseMB = minimumFloorMB - editorBaseMB`), reflejando la memoria requerida por el stack seleccionado (lenguaje, web, complementos y base de datos).
     3. `Espacio libre para los programas del alumno` (`usableMB = totalMB - editorBaseMB - stackBaseMB`), de modo que `editorBaseMB + stackBaseMB + usableMB === baseRamMB`.
   - Se aplican candados de seguridad en frontend y backend (`AdminGovernanceService.CreateOfficialTemplate` y `UpdateOfficialTemplate`): bloqueo ante valores inferiores al mínimo requerido (`ErrRamBelowVitalFloor`) o superiores al límite del servidor (`ErrRamExceedsHostCapacity`), reajuste automático de la memoria al nivel recomendado si un cambio de stack en el Paso 2 eleva el piso por encima de la memoria configurada, y aviso preventivo cuando la cuota supera la memoria libre actual del servidor.

4. **Modo Avanzado con CodeMirror 6 (`<code-editor>`), Diagnóstico Estático en Vivo, Importación/Exportación y Blindaje de Publicación:**
   - Se reemplaza el uso de `<textarea>` planos en el Modo Avanzado por el componente institucional `<code-editor>` basado en CodeMirror 6, con extensiones de resaltado sintáctico para `dockerfile` y `shell` (`setup.sh`).
   - El editor de `Dockerfile` permanece siempre visible en el Modo Avanzado, permitiendo inspeccionar y modificar la receta Docker independientemente de si la imagen es construida localmente o resuelta directamente.
   - Se proveen herramientas directas en el navegador (sin dependencias externas) para **Importar/Descargar `Dockerfile`**, **Importar/Descargar `setup.sh`** y **Exportar `template-manifest.json`**.
   - Si el administrador edita manualmente el `Dockerfile` en el Modo Avanzado, se activa la guarda `hasCustomDockerfile = true`, preservando el código personalizado ante cambios en la selección visual, e incorporando un botón explícito `"Restablecer desde Selección Visual"` para reiniciar la sincronización.
   - **Diagnóstico Estático en Vivo del Dockerfile (`dockerfileDiagnostics`):**
     - Bloqueo por falta de instrucción `FROM`.
     - Bloqueo por uso de `:latest` o referencias a imágenes sin tag fijo de versión.
     - Advertencia ante comandos `apt-get install` que omitan el flag desatendido `-y` o `--assume-yes`.
   - **Blindaje de Publicación de Plantillas (`requiresVerificationBeforePublish`):**
     - Si la plantilla requiere construcción local (`needsLocalBuild === true` o imagen `solv-local/stack:*`), el botón `"Publicar Plantilla Oficial"` se mantiene deshabilitado hasta que el entorno haya sido comprobado satisfactoriamente (`activeEnvTestJob()?.status === 'success'`) y la huella de la configuración verificada siga coincidiendo con la actual.
     - Si el Dockerfile presenta diagnósticos de severidad `error`, tanto la comprobación como la publicación se bloquean preventivamente.
   - **Validación en Servicio, no Solo en Interfaz:** `AdminGovernanceService.CreateOfficialTemplate` y `UpdateOfficialTemplate` rechazan con `ErrTemplateVerificationRequired` (HTTP `422 verification_required`) cualquier imagen `solv-local/stack:*` cuyo `verification_job_id` no apunte a un job con estado `success`, del mismo `tenant_id` y del mismo usuario autenticado, y con `verification_fingerprint` igual a la huella de la configuración efectiva del payload: imagen, tecnologías declaradas, entorno, comando de ejecución, tiempo límite, entrada de muestra, RAM base, Dockerfile y `setup_script`. La whitelist externa de registros se aplica únicamente a imágenes remotas, porque el tag local no proviene de ningún registro. La interfaz calcula la misma huella para detectar cambios posteriores a la comprobación y detener el envío antes de llegar al backend.
   - Se desmantela de forma definitiva el antiguo wizard multipaso (`template-create-modal`), redirigiendo cualquier acceso vía `?nueva=1` directamente a la ruta dedicada del Studio (`/admin/plantillas/nueva`).
   - Se separan los contratos de dominio y DTOs en `frontend/src/app/features/admin/models/admin-templates.models.ts`. `AdminTemplatesService` opera exclusivamente como servicio de transporte HTTP hacia la API REST (`/api/v1/admin/template-components` y `/api/v1/admin/templates/capabilities`), sin listas estáticas en memoria ni catálogos de respaldo locales.

5. **Centro de Gobernanza del Catálogo de Tecnologías (`ModelLibraryComponent`) y Control de Disponibilidad:**
   - Se enriquece la pestaña de Catálogo de Tecnologías integrando una barra de filtros contextuales (búsqueda multicampo en nombre, slug, paquetes y herramientas; perfil de catálogo; disponibilidad activa/inactiva) y visualización simétrica dual en tarjetas interactivas (`cards`) o tabla de auditoría (`table`) mediante `ViewSwitcherComponent`.
   - **Control de Disponibilidad y Persistencia Parcial:** Se incorpora un switch de activación/desactivación reactiva (`is_active`) para ocultar o restaurar tecnologías en el Constructor sin requerir su eliminación física. En el backend Go (`TemplateComponentsRepository.UpdateTemplateComponent`), se preserva la imagen base existente (`existing.BaseImage`) ante actualizaciones parciales si el DTO no provee una nueva, manteniendo la validación de obligatoriedad para componentes de ejecución (`runtime`).
   - **Detección Automática de Complementos Huérfanos:** El catálogo analiza dinámicamente si los complementos (`addon`) con compatibilidad específica cuentan con al menos un entorno de ejecución principal (`runtime`) activo en el sistema, señalizando alertas visuales para prevenir combinaciones rotas en el Constructor.
   - **Métricas de Memoria Transparentes:** Se diferencia con precisión entre complementos pasivos instalados en disco (`0 MB RAM (En disco)`) y complementos con proceso de fondo (`+X MB (Proceso activo)`), así como la clasificación por perfiles (`liviano`, `estándar` o `intensivo`) para entornos de ejecución principal.

6. **Arquitectura Modular Container-Presentational (Piezas Atómicas en Angular 22) y Segregación por Subdominio en Backend Go:**
   - **Frontend Angular 22 (Container-Presentational + Utilidades Puras):** Para evitar componentes monolíticos, los contenedores principales (`ComponentFormModalComponent`, `TemplateStudioComponent`, `ModelLibraryComponent`, `AdminTemplatesComponent`) delegan el renderizado en subcomponentes presentacionales standalone gobernados por `input()` y `output()` de Signals y extraen sus catálogos y reglas puras a módulos dedicados:
     - `component-form-modal`: separa `component-catalog.presets.ts` (perfiles oficiales de ecosistema, web y complementos), `component-ecosystem.utils.ts` (inferencia de familia, gestores compatibles y síntesis de comandos), `<catalog-preset-grid>` (tarjetas de 1 clic + barra parametrizable de versiones) y `<smart-icon-picker>` (barra de icono detectado + galería contextual).
     - `template-studio`: separa `template-studio.utils.ts` (síntesis visual, diagnóstico de Dockerfile, cálculo de piso vital y perfiles de RAM), `<studio-purpose-step>` (Paso 1 de propósito e identidad), `<studio-capacity-selector>` (Paso 3 de capacidad del aula y barra segmentada de memoria) y `<studio-summary-sidebar>` (panel lateral de resumen en vivo, verificación Docker y publicación).
     - `model-library` y `admin-templates`: separan `template-tech-detector.utils.ts`, `model-library.utils.ts`, `<template-models-section>` (vista de modelos oficiales) y `<template-categories-manager>` (gestor de categorías académicas con reordenamiento).
   - **Selección Accesible en las Tarjetas del Catálogo:** las tarjetas de las tres columnas son `<button>` nativos con `aria-pressed`, muestran la descripción del componente como texto visible y dejan el control de edición como botón hermano, de modo que teclado y lector de pantalla recorren cada tarjeta una sola vez. El layout pasa a una sola columna por debajo de 1100px (panel de resumen junto al formulario) y 720px (tarjetas), sin desplazamiento horizontal.
   - **Backend Go 1.26 (Segregación por Agregado dentro de cada Paquete Hexagonal):** Los repositorios PostgreSQL, servicios de dominio y handlers HTTP se dividen en archivos cohesivos por subdominio (< 520 líneas por archivo) sin alterar contratos públicos:
     - `infrastructure/storage/postgres`: `admin_students_repository.go`, `admin_templates_repository.go`, `admin_templates_lifecycle_repository.go`, `admin_catalog_models_repository.go`, `admin_drafts_repository.go`, `teacher_courses_repository.go`, `teacher_grading_repository.go` y `teacher_analytics_repository.go`.
     - `core/services`: `admin_governance_students.go`, `admin_governance_templates.go`, `admin_governance_emergency.go`, `admin_governance_components.go`, `evaluation_exercise_crud.go`, `evaluation_dryrun.go`, `evaluation_algorithm_runner.go` y `evaluation_database_runner.go`.
     - `delivery/http`: `admin_maintenance_periods_handler.go`, `admin_students_handler.go`, `admin_templates_handler.go`, `admin_catalog_models_handler.go` y `admin_components_handler.go`.

7. **Auto-Orquestación de Motores de Base de Datos, Aislamiento por Alumno y Scale-to-Zero:**
   > **Nota (2026-10-29):** el contrato de un único motor satélite por plantilla y el aislamiento por prefijo de claves descritos en esta sección quedan reemplazados por el ADR-050. Los contenedores, la red interna y el scale-to-zero siguen vigentes; la cardinalidad, la capacidad y el aislamiento se rigen desde el ADR-050.
   - **Motores como contenedores satélite bajo demanda:** cuando la plantilla del ejercicio declara un motor `managed_container`, al iniciar o reactivar el laboratorio se asegura el contenedor `solv-sat-<engine>` (`mysql:8.4`, `mariadb:11.4`, `mongo:7.0`, `redis:7.2-alpine`) con volumen nombrado persistente `solv_sat_data_<engine>`, techo de memoria en cgroups (`256 MB` en MySQL/MariaDB/MongoDB, `96 MB` en Redis) y `no-new-privileges:true`. La sintonización liviana viene por argumentos del motor: `--innodb-buffer-pool-size=64M --performance-schema=OFF --max-connections=100` en los relacionales, `--wiredTigerCacheSizeGB 0.25 --quiet` en MongoDB y `redis-server --maxmemory 64mb --maxmemory-policy allkeys-lru --appendonly yes` en Redis. Antes de devolver el endpoint se ejecuta un comando de readiness dentro del contenedor con backoff acotado a 30 s.
   - **Red interna dedicada (`solv-satellites-net`):** los motores y los laboratorios que los usan conviven en una red bridge propia, resuelta por DNS interno de Docker como `solv-sat-<engine>`, sin `PortBindings`: ningún motor se publica al host ni comparte la red de Traefik, así que los laboratorios de distintos alumnos no se alcanzan entre sí. Si la conexión del laboratorio a esa red falla, el arranque se aborta y el contenedor se descarta en lugar de dejar un laboratorio sin su base de datos.
   - **Aislamiento por alumno y materia:** en MySQL y MariaDB cada par alumno/materia recibe base `solv_std_<student>_<subject>` y usuario exclusivo `u_<12hex>` con contraseña derivada por HMAC-SHA256 de `studentID + ":" + subjectID` (clave `SOLV_SATELLITE_SECRET`, con el secreto de sesión del nodo como respaldo). Las credenciales son deterministas, de modo que reconectar el mismo laboratorio reescribe la misma base, el mismo usuario y los mismos permisos sin acumular objetos huérfanos. MongoDB y Redis se aíslan por espacio de nombres (`solv_std_<student>_<subject>` y prefijo de claves respectivamente) dentro de la red interna.
   - **Inyección transparente y `db_init_script` multi-motor:** el laboratorio recibe `DATABASE_URL` y variables afines del motor declarado, y el `db_init_script` del ejercicio se aplica una sola vez por `exercise_id` sellado en `_solv_exercise_migrations` dentro de la base del alumno, con el mismo contrato idempotente que la ruta PostgreSQL de aula. Si el motor no puede levantarse, el inicio falla en lugar de arrancar un laboratorio roto.
   - **Scale-to-Zero:** al hibernar, pausar o terminar un laboratorio —y en cada ciclo de `QoSOrchestratorWorker`— `WorkspaceService.ReconcileIdleManagedSatellites` resuelve qué motores gestionados usa realmente cada workspace en estado `running` y detiene el contenedor de todo motor que quedó en `0`. Detener no elimina: el volumen y los datos sobreviven, y la próxima sesión reactiva el mismo contenedor.

## Consecuencias

- **Positivas:** Arranque instantáneo (< 1 segundo) para los estudiantes sin descargas repetidas en horario de clase; experiencia de desarrollo y administración de nivel Enterprise con edición de código real en el navegador; diagnóstico preventivo que evita imágenes rotas en el registro o construcciones congeladas; blindaje absoluto que impide publicar imágenes locales no probadas; operación sin conexión asegurada tras la publicación; soporte extensible para gestores de paquetes modernos (`uv`, `cargo`, `go`, `composer`).
- **Positivas (motores de base de datos):** la Columna 3 queda gobernada por el catálogo y no por variables de entorno declaradas por SSH, así que habilitar MySQL, MariaDB, MongoDB o Redis deja de exigir trabajo de infraestructura; un aula que no está usando un motor no paga su RAM (`256 MB` o `96 MB` se liberan al apagarse), y el aislamiento por credenciales derivadas evita que un alumno lea la base de otro. Los datos sobreviven a los apagados porque el volumen es nombrado y el contenedor no se elimina.
- **Negativas / Reducción de impacto:** el primer arranque de un motor descarga su imagen (una sola vez, con pull single-flight) y tarda hasta 30 s en declararse listo; una clase entera que entra al mismo tiempo comparte un único contenedor de motor, cuyo techo de RAM se define por especificación (`256 MB`/`96 MB`) y no por alumno, de modo que el consumo de un aula completa es acotado y predecible. Los motores NoSQL se aíslan por espacio de nombres dentro de la red interna y no por credenciales del motor: queda como límite explícito del diseño y como candidato a endurecer con autenticación nativa en una iteración posterior.
